## 1. エグゼクティブサマリー

Section 14（Dashboard and Self-Contained Report QA）の実装計画策定において、作成者が提示した初版（Commit `de6f1a1`）は、独立レビュアー（GPT-5.6 Sol）によるレビュー後の改訂版（Commit `f0b6ec5`）と比較して著しく粒度が粗く、データ契約や統計原則への踏み込みが不十分な**杜撰な計画書**であった。

本稿では、なぜこのような不備が発生したのかについて、認知バイアス、プロセス上の欠陥、統計アーキテクチャ理解の甘さの観点から根本原因を徹底的に分析する。さらに、今後同様の粗雑な計画書を二度と作成せず、初版から確定版レベル（Plan Review後レベル）の堅牢・精密な計画書を作成するための制度的・技術的な再発防止策（運用規約およびセルフレビューチェックリスト）を策定する。

## 3. なぜ杜撰な初回計画になったのか（根本原因の分析）

上記の欠陥が発生した根本原因を、以下の 4 つのメカニズムに分解して自己批判的に分析する。

### 3.1 タスク文面の表層的トレース（Premature Closure と Shallow Planning）

- **現象**: OpenSpec `tasks.md` に記載されたタスク項目（14.1〜14.9）のテキストを、体裁よくテーブルに転記・要約しただけで「計画書が完成した」と錯覚した。
- **原因**: 課題の難易度判定（Adaptive Reasoning）において、Section 14 を「単なる HTML / CSS レポートの体裁調整（Low〜Medium難度）」と過小評価した。その結果、データパイプライン（R の計算層 $\to$ `summary_df` $\to$ HTML レンダリング層）の内部構造や契約を深掘りせず、表面的な「見た目」の要件整理で思考を停止（Premature Closure）させた。

### 3.2 既存コードの盲従と無批判な受け入れ

- **現象**: 既存の `comparative_reporting.R` にすでに `tr style="background-color: ..."` や `row$badges` が実装されていたため、「既存の枠組みに少し手を入れるだけで済む」と無意識に前提を置いてしまった。
- **原因**: 既存コード自体がプロトタイプ段階の暫定実装であり、リポジトリの「統計哲学（次元の分離原則：効果量、方向、実務領域、精度の混同禁止）」に違反しているという疑いを持たなかった。シニアエンジニア・統計解析担当としての批判的検証（Independent Review）を怠り、既存のコードに引っ張られて誤った設計を追認した。

### 3.3 一次情報（コード・スキーマ）の直前照合の怠慢

- **現象**: バッジ名として `ZERO_EVENTS` という非実在の名称を平然と書き込んだ。
- **原因**: 「ゼロイベントに関するバッジだから `ZERO_EVENTS` だろう」という安易な推測・記憶依存（Hallucination / Guesswork）が混入した。リポジトリ内の既存スキーマやテストコードを ripgrep で検索して確認すれば数秒で防げた初歩的な確認ミスである。

### 3.4 「表示層で何とかする」という責任境界の曖昧さ

- **現象**: `summary_df` へのデータ搬送を明記せず、HTML 生成時に適当に数値を拾って判定させようとした。
- **原因**: 統計エンジン、要約データ構造（Provenance）、プレゼンテーション層の「責務の分離」に対する意識が希薄だった。表示層が元の raw counts を見て「$x_R == 0$ だから警告を出す」というような処理を行うと、上流のモデル（Bayesian なのか Bootstrap なのか、Person-time なのか）ごとの厳密な診断情報と乖離するリスクがあることを見逃していた。

## 4. 再発防止策：初版から「最新報告書レベル」の計画書を作成するための運用規約

今後、二度とこのような杜撰な計画書を作成しないため、計画書策定プロセスに以下の **「5大鉄則」** および **「事前自己レビュー（Pre-Submission Gate）」** を義務付ける。

### 4.1 計画書策定における 5大鉄則（Iron Laws for Implementation Planning）

1. **データ契約先行の原則（Data / Provenance First）**:
   - UI やレポート、HTML、出力を変更する計画では、**必ず「どのデータ構造（DataFrame / JSON / Object）に、どの canonical な指標を搬送するか」をテーブル定義レベルで先行明記**すること。
   - 表示層（HTML/Markdown）での ad-hoc な再推論や再計算を計画段階で禁止する。

2. **統計哲学・概念分離の構造監査（Strict Semantic Separation）**:
   - リポジトリの基本哲学（Effect Size, Direction, Practical Difference, Precision, Diagnostics の分離）と視覚表現（色、レイアウト）が整合しているかを必ず監査する。
   - 実務領域の色相（Hue）を行全体に適用して他列を汚染するような設計は、いかなる場合も排除する。

3. **一次情報の完全照合（Zero-Guesswork for Identifiers）**:
   - バッジ名、コード値、エラー識別子、関数名、列名は、必ず `grep_search` や `view_file` を実行し、既存コード・スキーマ・テストの出力から 1 文字の狂いもなく完全一致で引用すること。記憶や推測での命名を厳禁とする。

4. **テストマトリクスと境界値の義務化（Concrete Test Matrix Requirement）**:
   - 「テストを実装する」という抽象的表現を禁止し、計画書内に必ず **Fixtures（正常系・異常系・境界系）、Checks（検証論理）、Expected Results（期待値）** を表形式で明記すること。

5. **環境非依存性と包括的監査（Cross-Platform & Fail-Safe Design）**:
   - パス監査や依存関係チェックは、macOS だけでなく Linux（`/home/`, `/tmp/`）、Windows（ドライブレター `C:\`、UNC パス `\\`）、および `file://` プロトコルを網羅すること。
   - 外部ツール（サブエージェント等）に依存する検証は、それが動作しなかった場合のフォールバック（手動・ローカルレンダリング手順）を最初から計画に組み込むこと。

## 5. 計画書提出前の自己批判的チェックリスト（Pre-Submission Checklist）

計画書をユーザーに提示する直前に、AI 自身が内部で「独立した批判的 Reviewer（GPT-5.6 Sol 視点）」に切り替わり、以下の 6 項目をセルフチェックする。**1項目でも「No」があれば提出を中止し、計画書を自己修正する。**

- [ ] **Q1. データの流れ（Provenance）**: 表示層が必要とするすべての情報は、上流のデータ構造に明示的に定義されているか？表示側で勝手に推測・計算していないか？
- [ ] **Q2. 一次情報との完全一致**: 計画書内の定数・バッジ名・列名・関数名は、コードベースの実物と `grep` 等で完全一致を確認したか？推測で書いた単語はないか？
- [ ] **Q3. 論理的無矛盾性**: 定義の重複（例: alpha 値と override 色の二重定義）や、前後の記述の矛盾はないか？
- [ ] **Q4. ドメイン・統計原則への合致**: 概念分離（効果量・方向・実務領域・精度）がレイアウトや CSS 設計に反映されているか？行全体の安易な着色などで原則を破壊していないか？
- [ ] **Q5. 具体的テストマトリクス**: テスト対象の Fixture（U0〜U3、ゼロイベント、不安定データ、Null delta）と検証内容が具体的に定義されているか？
- [ ] **Q6. 環境非依存性**: Windows / Linux / macOS の差分、パス形式の網羅性、ツール実行失敗時の代替手段が考慮されているか？

## 6. 結論

今回の初版計画書における不備は、能力の限界によるものではなく、**「表面的なタスク転記による思考停止」「既存コードの無批判な受け入れ」「一次情報確認の怠慢」というプロセスの甘さ**に起因するものであった。

本稿で策定した「データ契約先行の原則」「テストマトリクスの義務化」「事前自己レビューチェックリスト」を今後の作業において厳格に遵守し、次回以降のすべての計画書において、初版から確定版水準の品質を提供することを誓約する。
