## 1. 背景と目的

`docs/reference` は、本リポジトリにおける統計数理・分析契約の正本リファレンスである。2026-09-12 の読み取り専用点検では、内部 Markdown リンクおよび CRR（条件付きセル順位再現性）の既存実装・OpenSpec 仕様との対応は確認できた一方、以下の是正対象を確認した。

1. 3次元表における ARM Lift と M1 セル別 $O/E$ を一般に同値と読める表現。
2. DB 基盤の設計原則を本統計リポジトリの正本責務として置くことによる、`rwd-mysql-skill-toolkit` との責務境界の重複。
3. MySQL の `DATETIME` と `TIMESTAMP` を、ともに「JST で一貫」と扱う時刻意味論の不正確さ。
4. 調整済み残差を漸近近似であると説明しながら「厳密」と表現する、疎セルでの解釈境界を曖昧にする記述。

本計画は、上記を文書上で是正し、実装・仕様・データを変更せずに、統計上および運用上の誤読を防ぐことを目的とする。

## 3. 是正方針

### 3.1 ARM Lift と 3次元対数線形モデル

`advanced_analysis.md` の Lift の説明を次の境界に改める。

- 2元周辺表 $(A,B)$ で相互独立を基準にすると、Lift $P(A,B)/(P(A)P(B))$ は当該2元表のセル別 $O/E$ に対応する。
- 3元表の M1 セル別比は $P(A,B,C)/(P(A)P(B)P(C))$ であり、周辺化した $A \to B$ Lift と一般には同値ではない。
- 第3変数を扱うときは、周辺 Lift、$C$ ごとの層別 Lift、M1/M5 等の基準モデルに対するセル診断を、異なる estimand として分離する。

これにより、既存の「シンプソンのパラドックスに脆弱」という注意は維持しつつ、比較対象の数理を正確にする。

### 3.2 DB 文書の責務境界と時刻契約

`DB_Best_Practices.md` は、DBMS を構築・運用する一般ガイドではなく、分析用のカテゴリカル集計表を安全に受け渡す際の補助的契約として位置づける。

- DB/SQL の実装・運用詳細の正本は `rwd-mysql-skill-toolkit` 側で管理することを明記する。
- 保存時刻は、時刻瞬間を表す列なら UTC 保存と接続セッションのタイムゾーン管理を原則として明示する。
- `TIMESTAMP` は接続セッションのタイムゾーンにより変換され得ること、`DATETIME` はタイムゾーン情報を保持しない暦時刻であることを区別する。
- JST はレポート表示・Artifact 時刻などの表示規約として明示的に変換する。元データの意味が「現地の壁時計時刻」のみである場合は、解釈基準を別途データ契約で定義する。

### 3.3 調整済み残差の近似条件

`stats_categorical.md` では、式 $r_{S,i}$ と $T_i^{\rm score}=r_{S,i}^2$ の定義上の関係を維持する。その上で、標準正規・自由度1カイ二乗による解釈は正則性と十分な期待度数を前提とする漸近近似であり、観測ゼロ・小期待度数・高レバレッジ・境界推定では使用しないと明記する。既存の Stability/Quarantine 契約への参照を加え、表現を「厳密な残差」から「レバレッジ補正された調整済み残差」に改める。

## 4. 実施手順

1. 編集開始前に `git status --short --branch` と、4対象文書に限定した `git diff` を確認し、既存差分（特に `README.md`）を保持する。
2. 3.1〜3.3 の方針に沿って、対象4文書だけを最小限編集する。各文書の `update` を実編集時点の JST に更新する。
3. リポジトリ内 Markdown リンクを、リンク元ディレクトリ基準で機械的に再解決する。
4. `git diff --check` を実行し、今回の編集による空白・改行エラーがないことを確認する。作業前からある対象外差分の警告は、今回の修正として扱わない。
5. 対象4文書の差分を読み直し、次を確認する。
   - 2元周辺 Lift と3元セル診断を同値としていない。
   - DB の正本責務を越境していない。
   - `TIMESTAMP` と `DATETIME` の意味を混同していない。
   - 調整済み残差の漸近近似と Quarantine の境界が一貫している。
6. 終了時に `git diff -- docs/reference` と `git status --short --branch` を確認し、Codex が加えた変更と既存変更を区別して報告する。

## 6. リスクと判断境界

- 既存文書には利用者の未コミット CRR 追記が含まれる。対象部分を編集する場合も、その内容・更新日時を不用意に上書きしない。
- DB の内容を全面削除すると既存利用者への参照断絶を起こし得るため、本計画では削除ではなく責務と適用範囲の明確化を採用する。
- 0.5連続性補正、CRR の品質ゲート、閾値そのものは今回の点検対象ではあるが、統計エンジンの変更を伴うため改定対象外とする。
- 数理文献の解釈に新たな仕様変更が必要と判明した場合は、文書だけで断定せず、計画を更新して再承認を得る。

## 7. 承認後に行うこと

本計画の承認は、Section 2.1 の4文書への限定編集および Section 5 の検証だけを許可する。Artifact の追加作成、実装・Schema・OpenSpec変更、テスト実行、commit、push、外部書込みは別途承認が必要である。
