# 2. QA0001-H01 — CLOSED

## Original Finding

Dependency-structure safety depended on fixed column-name heuristics, allowing a higher-level cluster or matched structure with a noncanonical name to evade the independence guard.

## Repair Verified

`.agents/shared/pass0_routing.R` now introduces:

```text
REPEATED_ROWS_ALLOWED_KEYS
HEURISTIC_MATCHED_COL_ALIASES
HEURISTIC_CLUSTER_COL_ALIASES
normalize_declared_cols()
resolve_dependency_structure_cols()
```

`repeated_rows` now requires:

```text
no_other_subject_dependence_confirmed = true
```

and optionally accepts:

```text
cluster_cols
matched_cols
```

Configured columns are merged with heuristic aliases:

```text
effective matched cols =
  heuristic matched ∪ declared matched

effective cluster cols =
  heuristic cluster ∪ declared cluster
```

The implementation also verifies that explicitly declared dependency columns exist in the input data.

### Noncanonical Guards Added

The heuristic aliases now include examples such as:

```text
facility_id
hospital_id
clinic_id
institution_id
ward_id
matched_group_id
matched_pair_id
matching_id
match_group_id
```

More importantly, arbitrary noncanonical names can be declared explicitly in configuration.

### Test Coverage Added

`tests/test_pass0_routing.R` includes negative fixtures for:

- `facility_id`
- `hospital_id`
- configured custom cluster column
- `matched_group_id`
- configured custom matched column
- absent `no_other_subject_dependence_confirmed`

### Verdict

The prior High finding is **CLOSED**.

The architecture no longer depends solely on column spelling. Unknown semantic dependence that cannot be mechanically inferred is addressed through explicit caller attestation.

# 4. QA0001-M02 — CLOSED

## Original Finding

`routing_decision.json` declared `schema_version = "pass0-routing-v1"` but no corresponding JSON Schema existed.

## Repair Verified

New file:

```text
schemas/pass0-routing-v1.json
```

The schema defines:

- base routing metadata;
- target engine/module;
- inferential semantics;
- design / estimand;
- input/config provenance hashes;
- repeated-row diagnostics;
- `subject_level_counts`;
- canonical `engine_input`.

When `diagnostics.repeated_rows` is present, the schema conditionally requires:

```text
subject_level_counts
engine_input
```

The schema constrains integer/nonnegative events and positive totals.

A negative fixture removes `engine_input` from a repeated-row routing payload and expects schema rejection.

### Verdict

The original M02 requirement is **CLOSED**.

### Optional Future Tightening

The schema currently enforces:

```text
repeated_rows diagnostics
    -> subject_level_counts + engine_input
```

but does not prohibit a malformed external payload from supplying `engine_input` without repeated-row diagnostics.

This is not required to close the original M02 and does not affect generated runtime artifacts, but a future atomic-state hardening may add the reverse constraint.

## Residual Finding: QA0001-M03A

**Severity:** Medium  
**Gate impact:** Non-blocking / post-acceptance hardening

### Evidence

`schemas/pass0-config-v1.json` uses Draft-07 keywords including:

```text
minLength
uniqueItems
```

For example:

```json
"cluster_cols": {
  "type": "array",
  "items": { "type": "string", "minLength": 1 },
  "uniqueItems": true
}
```

However the local validator inside:

```text
tests/test_comparative_schemas.R
```

does not implement `minLength` or `uniqueItems`.

The test helper implements, among others:

```text
type
enum
const
minimum / maximum
exclusiveMinimum / exclusiveMaximum
required
properties
additionalProperties
items
minItems
if / then / else
not
$ref
```

but no logic for:

```text
minLength
uniqueItems
```

Therefore the local test can falsely report a payload as schema-valid when a real Draft-07 validator must reject it.

Example cases:

```yaml
cluster_cols:
  - facility_id
  - facility_id
```

or:

```yaml
cluster_cols:
  - ""
```

The runtime rejects these through `normalize_declared_cols()`, and the canonical JSON Schema is correctly written, but the local "Draft-07" validation harness does not independently prove those schema constraints.

### Additional Representation Note

Runtime accepts an R character value such as:

```r
cluster_cols = "custom_site"
```

while the canonical JSON schema defines `cluster_cols` as an array.

This can be defensible as R-side normalization of a one-element JSON array, because JSON parsing may collapse arrays into vectors depending on parser settings. It should, however, be explicitly documented as a runtime representation adapter rather than treated as proof of JSON-level schema parity.
