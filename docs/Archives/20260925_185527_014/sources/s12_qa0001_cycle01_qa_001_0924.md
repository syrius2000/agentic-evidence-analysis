# QA0001-H01 — Dependency Structure Can Evade the Guard Through Noncanonical Column Names

**Severity:** High  
**Requirement:** S12-1 / S12-4  
**Verification:** Static code review; not dynamically reproduced

### Evidence

`.agents/shared/pass0_routing.R` lines 128–129 detect structures only through fixed column names:

```r
matched_cols <- names(df)[col_names_lower %in% c(
  "matched_set", "matched_set_id", "set_id",
  "pair_id", "match_id", "stratum_id"
)]
cluster_cols <- names(df)[col_names_lower %in% c(
  "cluster", "cluster_id", "site_id", "center_id"
)]
```

`schemas/pass0-config-v1.json` lines 45–55 defines `repeated_rows`, but provides no explicit `cluster_cols`, `matched_cols`, or equivalent dependency-structure declaration.

Tests exercise canonical names only:

- `site_id`: `tests/test_pass0_routing.R` lines 206–209
- `pair_id`: lines 210–213
- `set_id`: lines 214–217

### Failure Scenario

An input may contain a real higher-level dependency such as:

```text
subject_id | arm     | outcome | facility_id
T1         | Drug_A  | 0       | F01
T1         | Drug_A  | 1       | F01
T2         | Drug_A  | 0       | F01
R1         | Placebo | 0       | F02
R2         | Placebo | 1       | F02
```

`facility_id` is not one of the recognized names. Multiple subjects share a facility, but Pass 0 can miss this dependency, collapse by subject, and route to the independence-assuming Beta-Binomial engine.

The same issue applies to unrecognized matched-structure names such as `matched_group_id`.

### Impact

The central Section 12 safety claim is that unsupported dependence is not silently treated as independent observations. The current implementation cannot guarantee that claim because correctness depends on column spelling rather than an explicit dependency contract.

### Recommendation

Make dependency structure explicit in the repeated-row configuration. At minimum support configured cluster and matched columns, merge them with heuristic detection, and require explicit confirmation that no other subject dependence is known.

Required negative fixtures should use noncanonical names such as:

- `facility_id`
- `hospital_id`
- `matched_group_id`

# QA0001-M01 — Derived Subject Counts Are Recorded but the Engine Handoff Is Not Executably Proven

**Severity:** Medium  
**Requirement:** S12-2  
**Verification:** Static code/test review

### Evidence

`.agents/shared/pass0_routing.R` lines 343–345 only adds:

```r
routing_decision$subject_level_counts <- inspection$subject_level_counts
```

The routing artifact separately records the target engine at lines 330–336.

The test validates the engine name and the derived counts:

`tests/test_pass0_routing.R` lines 172–176.

No Section 12 test invokes `run_independent_beta_binomial()` using those derived counts.

### Impact

The implementation proves a **declarative routing decision**, not an executable count handoff. A downstream caller can still ignore `subject_level_counts` and read the original repeated-row input incorrectly.

### Recommendation

Add a canonical machine-readable `engine_input` block, for example:

```yaml
engine_input:
  contract: independent_binary_counts_v1
  target_events: 1
  target_total: 2
  reference_events: 1
  reference_total: 2
  source: repeated_rows_any_event_collapse
```

Add an integration test that passes exactly those values into `run_independent_beta_binomial()`.

# QA0001-M02 — `pass0-routing-v1` Has No Canonical JSON Schema

**Severity:** Medium  
**Requirement:** deterministic routing artifact / S12-2  
**Verification:** Repository schema inspection

### Evidence

The implementation emits:

```text
schema_version = "pass0-routing-v1"
```

but the repository schema directory contains `pass0-config-v1.json` and no `pass0-routing-v1.json`.

Section 12 adds new machine-relevant fields:

- `subject_level_counts`
- `diagnostics.repeated_rows`

without a schema contract.

### Impact

A routing artifact can drift structurally while retaining the same schema-version string. Downstream consumption and QA cannot validate the artifact independently.

### Recommendation

Add `schemas/pass0-routing-v1.json`, including conditional requirements for repeated-row collapse and the proposed canonical `engine_input`.

# QA0001-M03 — Pass 0 Runtime Validation and Config Schema Are Not Demonstrated as a Single Contract

**Severity:** Medium  
**Requirement:** S12-1  
**Verification:** Static code/schema review

### Evidence

Runtime uses custom validation:

```r
validate_pass0_config(config)
```

while `pass0-config-v1.json` is a separate contract.

Examples of possible drift:

- runtime requires `subject_id_col`, `group_col`, and `outcome_col` to be distinct;
- the JSON schema does not express that cross-field inequality;
- schema sets `additionalProperties: false` within `repeated_rows`;
- runtime does not explicitly reject all unexpected `repeated_rows` keys.

No parity fixture matrix is present in `tests/test_comparative_schemas.R` for `pass0-config-v1.json`.

### Impact

The same config can be accepted by one validator and rejected by the other, undermining reproducibility of Pass 0 governance.

### Recommendation

Add shared valid/invalid config fixtures and run each through both:

1. `validate_pass0_config()`
2. Draft-07 schema validation

Document any intentionally runtime-only invariant.
