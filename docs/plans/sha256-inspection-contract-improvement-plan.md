# Pass 0 / Pass 1 SHA-256 契約の改善計画

## 1. 調査対象と結論

`Sha256-prblem.md` に記録された実行ログと、現在の実装を照合した。問題の直接原因は、Pass 0 の `inspection_results.json` が入力ハッシュを `file_sha256` として出力する一方、3 次元分析の Pass 1 入力検証が `input_sha256` を参照していることにある。

この不一致により、入力ファイル、`analysis_config.json`、および SHA-256 値が正しくても、`inspection$input_sha256` が `NULL` となり validate-only が「検分の入力ハッシュ不一致」で停止する。現行の Pass 0 を再実行するだけでは同じキーが再生成されるため、エラーメッセージが案内する復旧方法では解決しない。

## 2. 確認した問題点

### P0: 契約キーの不一致（ブロッカー）

- `.agents/shared/inspect_data.R` は `inspection_contract_version = "1.0"` と `file_sha256` を出力する。
- `.agents/skills/vcd-bayesian-evidence-analysis/templates/three_way/input.R` は `consultation.input_sha256` と、検分 JSON の `inspection$input_sha256` が一致することを要求する。
- したがって、共有 Pass 0 から 3 次元正本経路へ進む標準フローが接続できない。

### P1: 後方互換方針が未定義

既存の検分成果物は `file_sha256` を持つため、出力側を単に `input_sha256` へ置換すると過去成果物を読めなくなる。正式キー、旧キーの有効期間、両方が存在して値が異なる場合の扱いを契約として定義する必要がある。

### P1: ハッシュ計算手段が統一されていない

- Pass 0 は R パッケージ `digest` が利用できる場合だけ SHA-256 を計算し、利用できなければ `NULL` を出力する。
- Pass 1 は外部コマンド `shasum` を直接使用する。

同じ値を得る想定でも、依存関係と失敗動作が異なる。特に Pass 0 が成功扱いのままハッシュを `NULL` にできるため、問題が Pass 1 まで遅延する。

### P1: 回帰テストが契約接続を検証していない

既存の `inspect_data.R` テストは出力先、行数、引数形式を確認するが、ハッシュキーの存在・形式・実値、および生成した検分 JSON を 3 次元 validate-only が受理することを確認していない。このため、Pass 間の破壊的なキー変更を検出できなかった。

### P2: エラー分類とメッセージが原因を区別しない

現状は、次の異なる状態が同じ「検分の入力ハッシュ不一致。Pass 0を再実行」に集約される。

1. 検分 JSON に正式キーがない。
2. ハッシュ値の形式が不正または `NULL` である。
3. 検分時から入力ファイルが実際に変更された。
4. 正式キーと旧キーが併存し、値が矛盾する。

運用者が再実行で直る問題か、実装・成果物移行が必要な問題かを判断できない。

## 3. 改善方針

正式な契約名を **`input_sha256`** とする。移行期間中は Pass 0 が `input_sha256` と非推奨の `file_sha256` を同値で出力し、Pass 1 は以下の fail-closed 規則で読み取る。

1. `input_sha256` があれば正式値として使う。
2. 正式値がなく `file_sha256` があれば、旧成果物として受理する。
3. 両方があれば、同値の場合だけ受理する。
4. 不在、`NULL`、非文字列、または 64 桁の小文字 16 進数でない値は拒否する。
5. 両キーが異なる場合は曖昧なフォールバックをせず、契約矛盾として拒否する。
6. 読み取った検分ハッシュ、設定の `consultation.input_sha256`、実ファイルから再計算したハッシュの三者一致を要求する。

この方針により、新しい成果物の契約名を統一しながら、既存の正当な Pass 0 成果物を安全に移行できる。

## 4. 実装計画

### Phase 1: 共有 SHA-256 契約を明文化する

- `inspection_contract_version` を更新し、`input_sha256` を必須フィールドとして文書化する。
- `file_sha256` は後方互換用の deprecated alias と明記する。
- 値の形式、バイト列に対する SHA-256 であること、欠損時は Pass 0 自体を失敗させることを定義する。
- 旧キーの廃止条件は、リポジトリ内の fixture・例・文書が正式キーへ移行し、少なくとも一つの明示的な契約バージョン更新を経た後とする。

### Phase 2: Pass 0 の出力を修正する

- `.agents/shared/inspect_data.R` で SHA-256 計算失敗を成功成果物の `NULL` に変換せず、明示的な非ゼロ終了にする。
- `input_sha256` を正式出力する。
- 移行期間中は `file_sha256` に同じ値を出力する。
- ハッシュ計算を共有ヘルパーへ集約できるか検討し、Pass 0 と Pass 1 の依存・正規化・エラー動作を一致させる。

### Phase 3: Pass 1 の読取と診断を修正する

- `input.R` に検分ハッシュを解決する小さな関数を追加し、正式キー優先・旧キー fallback・二重キー矛盾拒否を一箇所で実装する。
- SHA-256 形式を比較前に検証する。値を暗黙に小文字化して不正な成果物を隠すのではなく、生成側の契約違反として扱う。
- 「キー不足」「形式不正」「alias 矛盾」「実入力変更」を個別のエラーメッセージにする。
- 現在の実ファイル対設定、および検分成果物対設定の二重照合は維持する。

### Phase 4: 回帰テストを追加する

最低限、次を自動化する。

1. Pass 0 出力に 64 桁の `input_sha256` があり、実ファイルの SHA-256 と一致する。
2. 移行期間中の `file_sha256` が正式キーと一致する。
3. 正式キーだけの検分成果物を受理する。
4. 旧キーだけの既存成果物を受理する。
5. 両キーが異なる成果物を拒否する。
6. 両キーがない、`NULL`、長さ不正、非 16 進文字を含む成果物を拒否する。
7. Pass 0 後に入力を 1 バイト変更すると拒否する。
8. 実際の `inspect_data.R` 出力から最小の有効設定を組み立て、3 次元分析の `--validate-only` が成功する end-to-end テストを追加する。

### Phase 5: 文書・例・fixture を移行する

- `SKILL.md`、設定例、品質契約で `input_sha256` を正式名称として統一する。
- リポジトリ内の固定 inspection fixture を検索し、契約バージョンとキーを更新する。
- `file_sha256` 参照は、互換コード、互換テスト、移行説明だけに限定されていることを静的チェックする。

## 5. 実施順序とコミット境界

1. **契約・テストを先行**: 期待する正式キーと互換ケースをテストで固定する。
2. **Pass 0 修正**: 正式キー出力とハッシュ失敗時の fail-fast を実装する。
3. **Pass 1 修正**: 互換読取、形式検証、原因別メッセージを実装する。
4. **fixture・文書移行**: 参照箇所を正式名へ揃える。
5. **全体回帰**: 共有 Pass 0、3 次元計算エンジン、設定 schema、統計基盤テストを実行する。

レビューと切り戻しを容易にするため、可能なら「契約テスト」「実装修正」「文書・fixture 移行」を独立コミットにする。

## 6. 完了条件

- 新規 Pass 0 成果物が `input_sha256` を必ず持ち、値が実入力と一致する。
- Pass 0 の実成果物を使う 3 次元 validate-only が成功する。
- 旧 `file_sha256` のみを持つ正当な成果物は移行期間中に限り成功する。
- 欠損・形式不正・二重キー矛盾・入力改変の各ケースが fail-closed で、原因を区別できる。
- ハッシュ計算不能を含む異常時に、Pass 0 が成功成果物を残さない。
- 関連する単体、統合、統計基盤テストがすべて成功する。

## 7. 対象外

- SHA-256 以外のハッシュ方式への変更。
- run ID や成果物ディレクトリ命名規則の変更。
- 統計モデル、推定量、可視化、Pass 2 の日本語ナラティブの変更。
- 既存の分析成果物を一括して書き換える移行ツールの作成（必要性が確認された場合は別課題とする）。

## 8. リスクと緩和策

- **共有スクリプトへの影響**: `inspect_data.R` は複数スキルが利用するため、キー追加は後方互換にし、削除は行わない。
- **互換処理の恒久化**: deprecated alias の用途をテストと文書で限定し、削除条件を明示する。
- **環境差**: `digest` と `shasum` のどちらかに偶然依存しないよう、サポートする計算経路と不足時のエラーをテストする。
- **誤った自動修復**: 二つのキーが矛盾する場合は片方を選ばず拒否し、監査可能性を優先する。
