# 実行成果物ライフサイクルと実行パス引き継ぎ契約

## Purpose

分析パイプライン（Pass 0 〜 Pass 3）において、出力親ディレクトリの決定、実実行（run）ディレクトリの一意確定、二重階層防止、実行メタデータの記録、および後続処理（Pass 2/3）への確定的パス引き継ぎとAI完了報告の標準規約を定め、結果の取り違えや無言上書きを防止して分析の再現性と運用安全性を担保する。

## ADDED Requirements

### Requirement: 出力親ディレクトリと実実行ディレクトリの明確な責務分離
分析パイプラインは、設定上の親ディレクトリと実際に計算成果物を格納する実行ディレクトリの責務を明確に分離しなければならない（MUST）。Pass 0 は案件および分析種別に応じた出力親ディレクトリ（`output_dir`）と実行識別子（`run_id`）を `analysis_config.json` に確定し、Pass 1 は親ディレクトリと `run_id` から実実行ディレクトリ（`run_output_dir`）を一意に導出して確保しなければならない（MUST）。親ディレクトリパスの末尾に既に実行プレフィックス（`run_` 等）が含まれている場合、重複してさらに下位に `run_` 階層を作成してはならず（SHALL NOT）、正規化された単一階層として実実行ディレクトリを決定しなければならない（MUST）。

#### Scenario: 通常の親ディレクトリから実実行ディレクトリを決定する
- **WHEN** `analysis_config.json` の `output_dir` に親ディレクトリ（例: `output/my_study/vcd_bayesian`）および `run_id`（例: `abc12345def67890`）が指定される
- **THEN** Pass 1 は親ディレクトリ直下に正規の実行プレフィックスを付与した実実行ディレクトリ（例: `output/my_study/vcd_bayesian/run_abc12345def67890`）を決定・作成する

#### Scenario: 既に実行ディレクトリ階層を含むパスが指定された場合の二重階層防止
- **WHEN** `analysis_config.json` の `output_dir` に既に実行プレフィックスを含むパス（例: `output/my_study/run_01`）が指定される
- **THEN** Pass 1 はさらに下位へ `run_<id>` をネスト作成せず、指定されたパス自体を実実行ディレクトリとして認識・正規化して二重階層化（例: `run_01/run_<id>`）を防止する

### Requirement: 確定的メタデータ記録と実行コンテキストの保存
Pass 1 は実実行ディレクトリの確定および計算完了後、実実行ディレクトリの絶対・相対パス、生成日時（JST）、入力設定ファイルのハッシュまたは内容、使用された `run_id`、および入力データパスを含む実行メタデータ（`run_meta.json`）を実実行ディレクトリ直下に記録しなければならない（MUST）。後続プロセスや監査者はこのメタデータを通じて実行時の前提と出力の正当性を検証できなければならない。

#### Scenario: 実行メタデータを実実行ディレクトリへ出力する
- **WHEN** Pass 1 の統計計算が完了する
- **THEN** 実実行ディレクトリ直下に `run_meta.json` が生成され、確定実パス、`run_id`、生成タイムスタンプ、入力データ情報が完全に記録される

#### Scenario: 設定と実実行パスのトレーサビリティを確保する
- **WHEN** 後続処理または利用者が実行メタデータ（`run_meta.json`）を参照する
- **THEN** どの `analysis_config.json` と入力データから生成された実行成果物であるかが曖昧さなく一意に追跡可能である

### Requirement: Pass 2 および Pass 3 への実実行ディレクトリの直接引き継ぎ
Pass 2（AI 考察・要約作成）および Pass 3（ダッシュボード生成）は、親ディレクトリ配下のファイル更新日時（mtime）に基づく暗黙的・推測的な最新実行探索に依存してはならず（SHALL NOT）、Pass 1 が確定した実実行ディレクトリのパスを直接引き渡されて実行されなければならない（MUST）。ダッシュボード描画エンジンまたはレンダラーに実実行ディレクトリが直接指定された場合、外部の親ディレクトリ走査や他 run の探索を行わず、指定されたディレクトリ内の成果物（`evidence_results.json`、`analysis_config.json`、`executive_summary.md` 等）を直接利用して描画を行わなければならない（MUST）。

#### Scenario: 実実行ディレクトリを直接指定してダッシュボードを描画する
- **WHEN** レンダラー（`render_dashboard.R` 等）に引数として実実行ディレクトリパスが直接渡される
- **THEN** レンダラーは探索処理をバイパスし、指定された実行ディレクトリ直下の成果物を読み込んで同一ディレクトリ内または指定先にダッシュボードを出力する

#### Scenario: 複数 run が存在する親ディレクトリでの結果取り違えを防止する
- **WHEN** 親ディレクトリ配下に複数の過去実行ディレクトリが存在する状態で Pass 2 または Pass 3 を実行する
- **THEN** 暗黙的な mtime 探索による別 run の誤結合を起こさず、指定された対象 run のデータのみを確実に処理する

### Requirement: ライフサイクル状態管理と既存実行の上書き防止
分析パイプラインは、新規分析の開始、既存実行の継続（Pass 2/3 の追加）、および再計算・上書きのライフサイクル状態を区別して管理しなければならない（MUST）。入力データや設定パラメータを変更した新規分析では必ず新しい固有の `run_id` を発行して独立した新規実行ディレクトリを作成しなければならない（MUST）。同一実行に対する段階的処理（Pass 1 後の考察作成やダッシュボード描画）は同一の実実行ディレクトリに対して成果物を追記しなければならない（MUST）。既に完了した実行ディレクトリに対して破壊的再計算を行う場合、利用者の明示的承認または強制フラグがない限り、既存成果物を無言で上書き・破壊してはならない（SHALL NOT）。

#### Scenario: 設定変更を伴う分析で独立した新規実行ディレクトリを確保する
- **WHEN** モデル項、対象変数、層別条件などの設定を変更して新規分析を実行する
- **THEN** 新たな `run_id` が割り当てられ、過去の実行結果を上書きせずに別個の実行ディレクトリに成果物が保存される

#### Scenario: 同一実行に対する段階的成果物の追記
- **WHEN** Pass 1 完了後に同一 run に対して Pass 2（AI 考察）または Pass 3（ダッシュボード描画）を実行する
- **THEN** 既存の計算結果を保持したまま、同一実実行ディレクトリ内に `executive_summary.md` や `dashboard.html` が追記・統合される

#### Scenario: 既存実行ディレクトリへの無言上書きの拒絶
- **WHEN** 既に計算成果物が存在する実実行ディレクトリに対して明示的な上書き指示なしに Pass 1 の再実行が試みられる
- **THEN** 処理は警告またはエラーとして中断され、既存成果物の保護が行われる

### Requirement: 標準ディレクトリ階層の配置規約
分析成果物の配置は利用目的とスキルの特性に応じた標準階層に従わなければならない（MUST）。実案件の正式分析では `output/<case_name>/<analysis_type>/`（例: `consultation/`, `vcd_bayesian/`, `vcd_categorical/`, `questionnaire/`）配下に各実行ディレクトリを配置し、手動試行やスモーク確認では `skill_out/<skill_name>/` 配下に配置しなければならない（MUST）。単一表分析（`vcd-bayesian-evidence-analysis`, `vcd-categorical-analysis`）では `run_<first16_id>` 形式、バッチ設問分析（`questionnaire-batch-analysis`）では `runs/<id>` 形式の実行ディレクトリ構造を維持しなければならない（MUST）。

#### Scenario: 実案件における分析種別の並列配置
- **WHEN** 特定案件に対して Pass 0 相談と複数手法（Bayesian と Categorical）を実施する
- **THEN** `output/<case_name>/` 配下の各分析種別ディレクトリ内にそれぞれの実行結果が整理して配置され、相互の成果物が混ざらない

#### Scenario: スキルごとの実行ディレクトリ形式の維持
- **WHEN** 各分析スキルが成果物を出力する
- **THEN** 単一表分析は `run_<id>` 形式、バッチ設問分析は `runs/<id>` 形式として整合性を保ち、既存の自動化連携を阻害しない

### Requirement: AI 完了報告の標準 4 大要素の提示
AI エージェントが分析・描画の完了または途中進捗を利用者に報告する際、利用者が成果物と実行コンテキストを即座に確認・検証できるよう、以下の 4 大要素を Markdown 形式で明確に提示しなければならない（MUST）：
1. メインレポート（HTML/Markdown）への直接相対リンク
2. 実実行ディレクトリ（全成果物が格納されている実パス）
3. 入力設定および統計結果ファイルへの直接相対リンク（`analysis_config.json`, `evidence_results.json`, `run_meta.json` 等）
4. パイプライン進行状態（Pass 1 完了、Pass 2 考察完了、Pass 3 ダッシュボード生成完了等）

#### Scenario: パイプライン全完了時の 4 大要素報告
- **WHEN** Pass 3 までのダッシュボード生成が正常に完了し、AI が完了を報告する
- **THEN** レポートリンク、実実行ディレクトリパス、設定・結果ファイルリンク、および完了状態が標準構造で提示される

#### Scenario: 途中段階における状態報告
- **WHEN** Pass 1 のみが完了し、Pass 2 の考察作成待ちの状態で AI が進捗を報告する
- **THEN** 実実行ディレクトリと Pass 1 成果物へのリンクが明示され、パイプライン進行状態として「Pass 1 完了 / Pass 2 考察未作成」であることが明示される
